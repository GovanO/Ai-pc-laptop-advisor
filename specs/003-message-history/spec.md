## User Scenarios & Validation *(mandatory)*

### User Story 1 - Store user and AI messages on the server (Priority: P1)

When a user sends a prompt to the chat and receives a response from the AI model, both messages are automatically persisted on the server.

**Why this priority**: This is the core value of the feature—capturing the conversation flow without requiring login or explicit save actions.

**Independent Verification**: A message can be sent through the chat, verified to be stored on the server, and confirmed to persist across sessions without user authentication.

**Acceptance Scenarios**:

1. **Given** a user submits a prompt, **When** the AI responds, **Then** both the user prompt and AI response are stored on the server.
2. **Given** messages are stored, **When** the conversation continues, **Then** new messages are added to the stored collection without overwriting previous ones (up to the limit).

---

### User Story 2 - Retrieve and display stored messages (Priority: P2)

The stored messages are retrievable from the server so the chat can display the conversation history when needed.

**Why this priority**: Retrieving messages enables the chat to show conversation history and validate that persistence is working correctly.

**Independent Verification**: Messages stored in a previous session can be fetched and displayed in a new session without any user login or authentication.

**Acceptance Scenarios**:

1. **Given** messages exist on the server, **When** a request is made to retrieve them, **Then** the server returns the stored messages in chronological order.
2. **Given** no messages exist, **When** a retrieval request is made, **Then** the server returns an empty list without error.

---

### User Story 3 - Maintain a rolling window of last 30 messages (Priority: P3)

The server maintains only the most recent 30 message pairs (user + AI response) to keep storage bounded.

**Why this priority**: This constraint prevents unbounded storage growth and keeps the feature simple and performant.

**Independent Verification**: After storing more than 30 message pairs, the oldest messages are automatically removed, and only the 30 most recent remain.

**Acceptance Scenarios**:

1. **Given** 30 message pairs are stored, **When** a new message pair is added, **Then** the oldest message pair is removed to maintain the 30-message limit.

---

### Edge Cases

- What happens when a user message is submitted but the AI response fails?
- How does the system handle rapid successive message submissions?
- What happens when storage fails temporarily (e.g., disk full or database error)?
- How are messages organized if multiple sessions/browser tabs submit messages simultaneously?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST accept user prompts and AI responses via the existing chat endpoint and store them on the server in `db.json` as both user and assistant chat history.
- **FR-002**: The system MUST store messages without requiring user login or authentication.
- **FR-003**: The system MUST maintain a rolling window of at most 30 message pairs (user prompt + AI response) in `db.json` on the server.
- **FR-004**: The system MUST provide an endpoint to retrieve stored messages in chronological order.
- **FR-005**: The system MUST ensure that message storage does not expose the DIAL API key or other sensitive configuration.
- **FR-006**: The system MUST handle storage errors gracefully and provide clear error messages to the client if message persistence fails.

### Key Entities *(include if feature involves data)*

- **User Message**: A text prompt submitted by the user to the chat.
- **AI Message**: A text response generated by the model and returned to the user.
- **Message Pair**: A container linking a user message to its corresponding AI response with metadata (timestamp, order).
- **Message History**: A collection of up to 30 most-recent message pairs stored in `db.json` on the server.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can send a prompt and receive an AI response, and both are persisted on the server without explicit save action.
- **SC-002**: Messages are retrievable from the server in the correct chronological order.
- **SC-003**: The server maintains a rolling window of at most 30 message pairs; older messages are automatically removed when the limit is exceeded.
- **SC-004**: Message storage works without login or user authentication, and no credentials are exposed in the stored data.
- **SC-005**: If message storage fails (e.g., disk error), the user sees a clear message about the failure, and the chat remains usable for future submissions.

## Assumptions

- Message storage uses a local JSON file (`db.json`) on the server (no external database setup required initially).
- Messages are stored per-session or globally without user-specific segmentation (no authentication context).
- Message pairs are simple text-based exchanges (no images, files, or complex attachments).
- The rolling 30-message window is sufficient for the initial use case; pruning strategy is based on insertion order (oldest first).
- The feature does not require search, filtering, or advanced retrieval capabilities beyond chronological order.
- Message storage is separate from the existing chat response flow and does not add significant latency.
